# Тестирование STO Booking

В проекте используются два уровня автоматических backend-тестов:

- unit-тесты проверяют сервисы изолированно и используют моки зависимостей;
- E2E-тесты отправляют HTTP-запросы через Supertest в настоящее NestJS-приложение
  и работают с отдельной PostgreSQL-базой без моков Prisma.

## Быстрый запуск E2E

Требуется только запущенный Docker Desktop. Локально устанавливать Node.js или
PostgreSQL не нужно.

Из корня репозитория выполните:

```powershell
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from backend-e2e
```

Команда:

1. собирает development-образ backend;
2. запускает отдельную PostgreSQL 17;
3. пересоздаёт тестовую схему и применяет все Prisma migrations;
4. выполняет seed каталога;
5. запускает Vitest и Supertest;
6. возвращает код завершения тестового контейнера.

После запуска удалите остановленные контейнеры:

```powershell
docker compose -f compose.test.yaml down --volumes --remove-orphans
```

PostgreSQL хранит данные в `tmpfs`. Она не подключена к development- или
production-volume. Дополнительно E2E-набор отказывается работать с базой, имя
которой не содержит `test` или `e2e`.

## Запуск unit-тестов из Docker

Unit-тестам база не требуется:

```powershell
docker compose -f compose.test.yaml run --build --rm --no-deps backend-e2e npm test
```

Проверка линтером:

```powershell
docker compose -f compose.test.yaml run --build --rm --no-deps backend-e2e npm run lint
```

## Где находятся тесты

- `apps/backend/src/**/*.spec.ts` — unit-тесты сервисов и health-check;
- `apps/backend/test/app.e2e-spec.ts` — HTTP E2E-сценарии;
- `apps/backend/vitest.config.ts` — конфигурация unit-тестов;
- `apps/backend/vitest.config.e2e.ts` — конфигурация E2E;
- `apps/backend/test/E2E_MATRIX.md` — матрица позитивных и негативных сценариев;
- `compose.test.yaml` — изолированное Docker-окружение E2E.

## Что проверяет текущий E2E-набор

### Health и каталог

- доступность backend и соединения с PostgreSQL;
- списки и детали услуг и СТО;
- услуги выбранной СТО;
- некорректные и несуществующие идентификаторы.

### Доступность времени

- формирование будущих слотов;
- шаг слотов и часовой пояс;
- невалидная дата;
- услуга, недоступная в выбранном филиале.

### Авторизация и профиль

- регистрация, вход, получение пользователя, изменение профиля и выход;
- нормализация логина;
- валидация полей;
- запрет назначения роли через публичную регистрацию;
- дубликат логина и неверные учётные данные;
- ответы `401` без сессионной cookie.

### Автомобили

- создание, список и удаление;
- некорректное название и дубликат;
- несуществующий автомобиль;
- отсутствие авторизации;
- невозможность удалить автомобиль другого пользователя.

### Бронирования

- гостевая и авторизованная запись;
- использование контактов профиля и сохранённого автомобиля;
- личный список записей;
- валидация тела и несуществующее предложение;
- запрет использования чужого автомобиля;
- два параллельных запроса на единственный пост: один получает `201`, второй
  получает `409`.

### Администрирование

- список, фильтрация и детали записи;
- допустимый переход статуса;
- невалидные фильтры и запрещённый переход;
- несуществующая запись;
- ответы `401` без авторизации и `403` для обычного клиента.

Полная сводка находится в
[`apps/backend/test/E2E_MATRIX.md`](apps/backend/test/E2E_MATRIX.md).

## Как добавлять новые тесты

При добавлении endpoint или бизнес-правила:

1. Добавьте успешный сценарий.
2. Добавьте применимые негативные сценарии: `400`, `401`, `403`, `404`, `409`.
3. Для правил, обеспечиваемых базой, используйте настоящую PostgreSQL, а не мок
   Prisma.
4. Не полагайтесь на фиксированные числовые ID или порядок других тестов.
5. Для записей используйте динамически вычисленную будущую рабочую дату.
6. Оставляйте тестовую базу чистой через общий `beforeEach`.
7. Обновите `apps/backend/test/E2E_MATRIX.md` и соответствующий раздел этого
   файла.
8. Если изменилась команда запуска или Docker-контур, обновите также `README.md`.

Название теста должно описывать наблюдаемое поведение API, а не внутренний метод.
Например: `returns 409 when two clients request the only available post`.

Перед отправкой изменений выполните E2E, unit-тесты и линтер.

## Интерпретация результата

Успешный прогон заканчивается строками `Test Files ... passed` и кодом `0`.
При проверке конфликтов PostgreSQL может вывести в лог ожидаемое сообщение о
нарушении уникального ограничения. Результат считается успешным, если Vitest
завершился с кодом `0` и проверил ожидаемый HTTP-статус `409`.
